# 原則：何を載せ、どう伝えるか

どの見本を使っても守る考え方。骨子を作るときと、仕上げの確認のときに読む。

## 1. 載せる情報を選ぶ

| 原則 | スライドでの意味 |
|---|---|
| 目的に則する | 発表の目的に当てはまる情報だけを選ぶ。当てはまらないものは削り、聞き手が判断や行動に移るまでの距離を縮める |
| 分解できる | 全体の数字から、聞き手が読み解ける単位まで分けて示せるようにする（全体のスライド → 内訳のスライド） |
| 違いに気づける | 突出した値や、変化の時期と傾向（上昇・下降）に気づけるようにする |
| 鮮度が高い | 使えるうちで最新のデータを使い、いつ時点の数字かを書く |

## 2. 組み立てる

- **骨格から決める。** まず何を何枚、どの順で見せるか（骨格）を決め、文言・色・形・グラフの表現はその後に詰める。骨格が決まらないうちに表現を詰めると手戻りが増える。
- **構造を伝える。** 全体から部分へ、階層になるように並べる。最初に全体がわかり、次に詳細へたどり着ける順にする。
- **適切な情報量にする。** 1枚に載せすぎない。多いときはスライドを分ける。
- **比較対象を出す。** 数字だけでは判断しにくいときは、目標値・平均値・前年の値・前年比などを並べる。
- 「複雑な操作を要求しない」は、スライドでは「読み解くのに説明が要る図を使わない」と読み替える（このハーネスの解釈）。

## 3. グラフを作る2つの原則

**知りたいことを知れる**

| 原則 | 内容 |
|---|---|
| シンプルにする | 冗長なデータや説明、装飾的な表現など、理解に不要な情報を取り除く |
| 意味のある順にする | 大小順・時系列順など、伝えたいことに合った順に並べる |
| 強弱をつける | 重要な情報だけ、色・大きさ・文字の太さを変えて目を引く |
| 待たせすぎない | スライドでは「1枚を読み終えるまでの時間を短くする」と読み替える（このハーネスの解釈） |

**誤解を生まない**

| 原則 | 内容 |
|---|---|
| わかりやすく表記する | 前提知識が要る表現や複雑な文を避け、タイトル・系列名・単位を丁寧かつ簡潔に書く |
| データを定義する | 何を対象に集めたデータか、数値の意味、いつ更新されたかを参照できるようにする |
| 表現を歪曲しない | 軸の範囲を恣意的に決めない。範囲を省略しない。差を誇張・矮小化しない |
| メタ情報を書く | データの出典、更新日、いつ時点の数値か、注釈、免責事項を書く |

## 4. 良い例・悪い例

| 良い例（Do） | 悪い例（Don't） |
|---|---|
| 全体の指標を先に置き、その詳細のグラフを続ける | 詳細の要素だけが並んでいる |
| 項目を大小順・時系列順など、意味のある順に並べる | 意味もなく五十音順で並んでいる |
| グリッド線は最小限。数値と直接関係のない文字は薄い色にする | 目盛線・説明文・小数点以下が必要以上に書いてある |
| 平面で描く | 3D、ドロップシャドウなど数値と関係のない装飾 |
| 色数を絞り、注目してほしい系列だけ色を付け、他はグレー | 全系列に別々の色を付け、どれに注目すべきかわからない |
| タイトルに内容とデータの種類を書く（例：「出荷台数（月次推移）」） | 何を表すかすぐにわからないタイトル |
| タイトル・凡例は短く端的に | 長く冗長なタイトル・ラベル |
| 凡例をグラフのすぐ隣に、グラフと同じ順で置く | 凡例が離れている、順番がグラフと逆 |
| 棒グラフの原点は0 | 原点が0でない |
| マーカーの形・線の種類・塗りの模様など、色以外でも系列を区別する | 色だけで区別している（白黒印刷で伝わらない） |

## 5. 図を主役にする（このハーネスの方針）

- 1枚の基本形は「**タイトル＋lead＋図**」。lead 以外の本文は、できるだけ図（カード・流れ・循環・層・関係図など）で表す。lead の字数の目安は `schema.mjs` の「共通」。
- 箇条書きは、図で表せないときだけ使う。使うときは、項目の文を削りすぎない。1項目で意味が通る長さにする（目安は全角25字以上）。
- 「文字を減らす」とは「箇条書きを図に替える」こと。箇条書きの文を短くすることでも、発表者ノートに移すことでもない。
- 書式チェックが、箇条書きの型（`title-body`・`text-diagram`・`two-column`・`do-dont`）の多さと、短すぎる項目を注意にする（数は `html-build/scripts/spec.mjs` の `BULLETS`）。

## 6. 聞き手に合わせた言葉と図（このハーネスの方針）

- **初めて出る専門用語は、その場で説明する。** `brief.md` の「聞き手と前提知識」に初学者が含まれるときは、専門用語（例：スタブ、Red → Green → Refactor）を、初めて出るスライドの lead か図の中で説明する。説明に1枚要るほどの用語なら、説明のスライドを足すことを人間に提案する。
- **資料の比喩は、正確な言葉に直す。** 資料の比喩をそのまま写さない（例：「強い頭で計画し、実務の頭で実装する」→「能力の高いモデルで計画し、別のモデルで実装する」、「安い頭で調べる」→「安価なモデルで調べる」）。
- **図が何を表すかを決めてから描く。** `idea` に、図が表す関係（原因と結果、比較、循環、層、包含など）を書く。箱を並べるだけの図にせず、囲みの見出し（例：「AI の性質（原因）」「手当てをしないと起きること」）でその関係を示す。
- **実装や製品の紹介は、現物と食い違わせない。** 手順や仕組みは、現物（リポジトリのファイル、公式ドキュメント）を読んで書く。同じ名前で別のものがあれば書き分ける（例：手順の中のその場の整理〔`/implement-tdd` の Refactor〕と、全体の点検のコマンド〔`/refactor`〕）。
