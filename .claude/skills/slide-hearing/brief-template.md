# brief.md の書式

`decks/<deck-id>/brief.md` は、スライドの前提（デッキ全体の認識合わせ：目的・聞き手・結論・長さ・進め方）をまとめるファイル。人間が用意した入力を `reference/` の md にしてから（`slide-intake/reference-format.md`）、AI が前提をここに集約し、足りないところを質問で埋めて磨く。最後に人間が承認する。スライドの中身の材料（数値、参考資料の本文）は `reference/` に置いたままにし、brief.md には書き写さない。

- 先頭の `---` で囲んだ部分（YAML）は、表紙・締め・PDF などにそのまま使う値。`outline.md` の先頭の設定と表紙（S01）・締めに写す。
- 本文は見出しごとの文章。見出しの名前は変えない（チェックのスクリプトが見出しで探す）。
- まだ決まっていない項目は空のままにする。推測で埋めない。該当しないと人間が答えた項目は「なし」と書く（空＝まだ聞いていない、「なし」＝聞いて不要とわかった）。
- 資料の一覧は `reference/index.md`（`reference.mjs` が作る）。brief.md には一覧を書かない。資料が md になっていないと、チェックがエラーにする。
- 書いた内容の出どころを「出どころ」の表に残す。資料の ID と md の見出し（`R-002 シート：9月 B3`、`R-001（チャット 10月17日）`）で書く。
- 入力どうしが食い違うときは、どちらかを選ばずに「確認したいこと」に書き、ヒアリングで聞く。
- 調べないとわからないこと（他社の事例、統計、制度など）は「調査が必要な項目」に書く。
- スライドの中身の材料（数値の根拠、各スライドに書く内容の詳細など）で足りないものは「構成で検討すること」に書く。ヒアリングでは聞かず、構成の検討（`slide-outline`）で扱う。
- 数値は計算しない。合計などが入力にないとき（Excel の数式で結果が保存されていないときも）は、自分で計算せず「構成で検討すること」に書く。

チェック：`node .claude/skills/slide-hearing/scripts/check-brief.mjs decks/<deck-id>/brief.md`（空の項目と、確認したいことの一覧を出す）

## 書式

```markdown
---
deck_id: 2026-10-17-report-automation   # YYYY-MM-DD-<短い英語名>
title: 月次レポート作成の自動化           # 表紙のタイトル（2行にするなら | で複数行）
subtitle: 2部門での3か月の試行をもとに、全部門への展開を提案します   # 表紙の副題（出さないなら「なし」。空はまだ聞いていない）
date: 2026年10月17日                     # 表紙の日付（必須。発表日など）
author:                                  # 表紙の発表者。org と name の両方（2行）・片方だけ・「なし」
  org: データ活用推進本部　データ管理部
  name: 山田 太郎
contact:                                 # 締めの問い合わせ先。text と email のどちらか・両方・「なし」
  text: 問い合わせ先：データ活用推進本部　データ管理部
  email: data@example.jp
pdf: false                               # PDF も作るか
max_subagents: 3                         # 調査・ファクトチェックで1回に呼ぶサブエージェントの数の上限（1〜10。既定 3）
factcheck: 最後に1回                      # ファクトチェックの時期：最後に1回（既定）／構成のあとと最後の2回
---

## 目的・この資料で決めたいこと

## 聞き手と前提知識

（聞き手の説明のあとに、前提知識を1行に1つ「- 概念：N割」で書く。N割は、聞き手の何割がその概念を説明できるか。例：- SQL の基礎：8割）

## 伝えたい結論（1文）

## 終わったあとの行動

（聞き手に、見終わったあとにしてほしいこと。なければ「なし」）

## 資料の種類

（1行目に「解説型」か「提案型」。解説型＝理解してもらう、提案型＝決めてもらう・動いてもらう）

## 発表時間・枚数の目安

## 調査が必要な項目

## 必ず入れる要素・入れない要素

## 構成の進め方

（1行目に「決まっている」「たたき台がある」「相談して決めたい」のどれか。2行目から、構成案の場所や守ってほしいこと）

## 信頼して使う資料

（参考資料が reference/ にあるときだけ聞く。1行に1つ、資料の ID（R-001）を先頭に書き、扱いを添える。ないときは「なし」。例：R-003（書籍の要約）は採用。原本との照合は不要）

## 構成で検討すること

（AI が書く。スライドの中身の材料で、足りないものや確かめたいこと。ヒアリングでは聞かず、構成の検討で扱う。空でもよい）

## 確認したいこと

（AI が書く。足りない項目、食い違い、聞きたいこと。ヒアリングで答えをもらったら消す）

## 出どころ

| 項目 | 出どころ |
|---|---|
| 目的 | R-001（チャット 10月17日） |
| 聞き手 | R-002（記入シート） |
| 数値 | R-003 シート：月次 B2:D14 |
```

## 事前記入シートとの対応

人間用の事前記入シート（`slide-intake/intake-form.md`、記入したものは `decks/<deck-id>/inputs/intake.md`。md にしたものは `reference/sources/`）は、次のように brief.md と1対1に対応する。

| シート | brief.md |
|---|---|
| 1. 何のための資料ですか | 目的・この資料で決めたいこと |
| 2. 誰が見ますか | 聞き手と前提知識 |
| 3. いちばん伝えたいことを1文で | 伝えたい結論（1文） |
| 3-2. 見終わったあと、してほしいこと | 終わったあとの行動 |
| 3-3. 資料の種類 | 資料の種類 |
| 4. 長さ | 発表時間・枚数の目安 |
| 5. 調べてほしいこと | 調査が必要な項目 |
| 6. 必ず入れるもの・入れないもの | 必ず入れる要素・入れない要素 |
| 7-1. 進め方 | 構成の進め方 |
| 7-2. 構成の中身 | `outline-draft.md`（構成の草案。slide-intake が言葉を変えずに写す） |
| 8-1〜8-3. タイトル・副題・日付 | title・subtitle・date |
| 8-4・8-5. 所属・氏名 | author の org・name |
| 8-6・8-7. 問い合わせ先・メール | contact の text・email |
| 9. PDF | pdf（要る→true） |
| 12. サブエージェントの数 | max_subagents（「おまかせ」→3） |
| 13. ファクトチェックの時期 | factcheck（「おまかせ」→最後に1回） |
| 10. 参考にする資料 | `inputs/` に写し、`reference/` の md にする。出どころの表に資料の ID で使う。「信頼して使う」と書かれた資料は「信頼して使う資料」 |
| 11. その他のメモ | 内容に応じて各項目へ。どこにも入らないものは「確認したいこと」 |

## 項目の意味と、他の工程での使われ方

| 項目 | 書くこと | 使われ方 |
|---|---|---|
| deck_id | `YYYY-MM-DD-<短い英語名>` | フォルダ名。`outline.md` の `deck_id` |
| title・subtitle | 表紙に出す文 | `outline.md` の `title` と S01 |
| date | 表紙の日付（必須） | S01 の `date` |
| author | 所属と氏名・氏名のみ・所属のみ・「なし」 | S01 の `author`。「なし」なら書かない |
| contact | 締めの問い合わせ先（text・email） | 締めのスライドの `contact`・`email`。「なし」なら書かない |
| pdf | PDF も作るか | `outline.md` の `pdf` |
| factcheck | ファクトチェックの時期。「最後に1回」（既定。空のときも）か「構成のあとと最後の2回」 | `make-slides` の工程の順と承認（`status.mjs`・`gate.mjs`）。「2回」は、数値や事実が結論を左右するデッキ（費用、効果の数値、他社事例など）に勧める |
| 信頼して使う資料 | 人間が調べ終えた資料や書籍の要約など、そのまま採用する資料（資料の ID と扱い） | `fact-checker` が、資料と一致した記述を確かめたものとする（`research-standards` の「信頼して使う資料」）。`factcheck.md` に扱いを1行で残す |
| max_subagents | 調査とファクトチェックで1回に呼ぶサブエージェントの数の上限（1〜10） | `research-standards`・`slide-factcheck` が、論点やスライドをこの数以下にまとめて呼ぶ。数が多いほど早く終わるが、トークンを多く使う |
| 目的・この資料で決めたいこと | 資料を読んだ人に何を決めてほしいか | 構成の検討の出発点 |
| 聞き手と前提知識 | 誰が聞き、何を知っているか。前提知識は「- 概念：N割」（聞き手の何割が説明できるか） | ファクトチェックの P1 の基準。過半数（5割）に満たない概念は前提知識から外し、構成で説明する（`slide-outline/structure-framework.md` 1章。チェックが注意を出す） |
| 伝えたい結論（1文） | 1文で。聞き手が見終わったときに言える状態（持ち帰りの1文） | 構成の軸。冒頭の答えの予告と、最後の回収（`structure-framework.md` 4章） |
| 終わったあとの行動 | 見終わったあとにしてほしいこと。なければ「なし」 | 締めのスライドの呼びかけ |
| 資料の種類 | 解説型か提案型 | 提案型は、現状とあるべき姿を交互に見せ、行動の呼びかけで終える（`structure-framework.md` 4章） |
| 発表時間・枚数の目安 | 例：15分・10枚 | 構成の枚数 |
| 調査が必要な項目 | 調べる論点と、確かめ方の候補 | 調査（researcher）の起点 |
| 必ず入れる要素・入れない要素 | 例：費用は必ず入れる、個人名は入れない | 構成の検討 |
| 構成の進め方 | 決まっている・たたき台がある・相談して決めたい | 構成の検討での AI の動き方（下の表） |

## 「構成の進め方」の選択肢

| 選んだもの | 構成の検討（`slide-outline`）での AI の動き方 |
|---|---|
| 決まっている | 人間の構成（スライドの並び、各スライドの内容）を変えない。調査とファクトチェックで見つけた問題は、構成を変えずに人間に報告し、直すかは人間が決める |
| たたき台がある | たたき台を土台に、調査をもとに修正案を出す。採用するかは人間が決める |
| 相談して決めたい | 目的と伝えたい結論から、AI が章立ての案を出し、相談しながら固める |
