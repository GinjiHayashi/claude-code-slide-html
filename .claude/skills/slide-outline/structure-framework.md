# 構成のフレームワーク（structure-framework）

スライドの構成（何を・どの順で・どう語るか）を、決まった手順と確かめられる項目で決める。技術の説明、提案、社内の勉強会など、聞き手に理解と納得を積み上げてもらうスライドが対象。

元は人間が書いた草案（slide-structure-framework.md）。ハーネスの工程と言葉に合わせて書き直した。手法の出典と、推測・独自に整理した範囲は、草案のまま末尾に残す。

## 0. ハーネスへの入れ方

- 工程は置き換えない。既存の工程（ヒアリング、構成、ファクトチェック）の中に差し込む。
- 既存の項目と同じ意味のものは、既存の名前を使う（例：持ち帰りの1文＝`brief.md` の「伝えたい結論（1文）」、アサーション＝`outline.md` の `title`）。
- ハーネスの原則「文章の良し悪しは AI がレビューしない」（CLAUDE.md 原則6）は守る。フレームワークは「AI が構成を作るときの手順」と「機械で確かめられる検査」として入れる。話が通るかなど、機械で決められないことは人が見る。

| 段階           | 差し込む工程                     | 置き場                                                              |
| -------------- | -------------------------------- | ------------------------------------------------------------------- |
| 1 ゴールの定義 | 1b ヒアリング                    | `brief.md`（この文書の1章）                                         |
| 2 知識マップ   | 2 構成の前半                     | `knowledge-map.md`（この文書の2章）                                 |
| 3 説明の順序   | 2 構成                           | 知識マップの層と、`outline.md` の並び（3章）                        |
| 4 ストーリー   | 2 構成                           | `outline.md`（冒頭の SCQA、各スライドの `question`）                |
| 5 スライド単位 | 2 構成                           | `outline.md`（1文の主張のタイトル、`new`・`uses`・`adept`）         |
| 6 確かめ       | 2 の「見せて、直す」、5 最終確認 | 検査（スクリプト）と、人の確認表（`design-reference/checklist.md`） |

要旨：

1. ゴールから逆算する。聞き手・前提知識・持ち帰りの1文を先に決め、知識の呪いとエレベーターテストで確かめる。
2. 知識マップ（前提の関係の有向非巡回グラフ）を作り、優先度を付ける。
3. 知識マップの層の順に説明する（基礎から応用へ。同じ層の中は具体から抽象へ）。
4. 前方参照をしない。あるスライドでは、それより後で説明する概念を使わない。
5. ストーリーは「問いの連鎖」で作る。冒頭は SCQA で問いを立て、各スライドは直前の問いに答え、次の問いを生む。
6. 1スライド1主張（Assertion-Evidence）。新しく出る抽象的な概念は ADEPT の順で説明する。

## 1. ゴールの定義（1b ヒアリング）

`brief.md` に書く。以降のすべての判断の基準になる。

| 項目          | brief.md の見出し    | 書くこと                                                                        |
| ------------- | -------------------- | ------------------------------------------------------------------------------- |
| 聞き手        | 聞き手と前提知識     | 誰が聞くか                                                                      |
| 前提知識      | 聞き手と前提知識     | 説明せずに使ってよい概念。1行に1つ「- 概念：N割」（聞き手の何割が説明できるか） |
| 持ち帰りの1文 | 伝えたい結論（1文）  | 見終わったときに、聞き手が言える状態を1文で                                     |
| 行動          | 終わったあとの行動   | 見終わったあとにしてほしいこと。なければ「なし」                                |
| 時間・枚数    | 発表時間・枚数の目安 | 発表時間と枚数の目安                                                            |
| 種類          | 資料の種類           | 解説型（理解してもらう）か提案型（決めてもらう・動いてもらう）                  |

- 前提知識に書いた概念は、知識マップの根（説明しない概念）として扱う。持ち帰りの1文は、知識マップのゴールになる。
- 項目を聞く文は `slide-hearing/questions.md`。

### 1-1. 前提知識を確かめる（知識の呪い）

詳しい人ほど「知らない状態」を想像できず、前提を飛ばすか、逆に詳細を盛りすぎる（知識の呪い）。

- 前提知識の各項目に「聞き手の何割が説明できるか」を書く。
- 過半数（5割）に満たない項目は、前提知識から外し、構成で説明する概念にする。`check-brief.mjs` が注意を出す。
- 迷う項目は、説明する概念にする（説明がくどくなる損より、理解が崩れる損のほうが大きいため。推測）。

前提知識を多く見積もると、知識マップの根がずれ、前方参照をしていなくても理解が崩れる（推測）。

### 1-2. 持ち帰りの1文を確かめる（エレベーターテスト）

- 持ち帰りの1文を、30〜45秒で口で説明できるか。できなければ、ゴールが大きすぎる。絞るか、デッキを分ける。
- 確かめるのは人。AI は判定せず、brief.md の確認を頼むときに問いかける（`slide-hearing` の手順5）。

## 2. 知識マップ（2 構成の前半）

構成の進め方が「たたき台がある」「相談して決めたい」のとき、章とスライドを決める前に作る。「決まっている」では作らない（人の並びを変えないため）。

- **知識マップ**：概念を点、前提の関係を矢印にした、循環のないグラフ。`A → B` は「B を理解するには A が要る」。
- **前提の関係**：B の説明（文・図・話す内容）の中で A の言葉や考え方を使うとき、A を B の前提にする。

### 2-1. 作り方

1. ゴール（持ち帰りの1文に当たる概念）を置く。
2. 「これを理解するには何が要るか」をくり返し問い、前提の概念を挙げる（逆算）。
3. 前提知識（1章。brief.md に書いたもの）にたどり着いたら、そこで止める。前提知識は表に書かない。
4. 各概念に1文の定義を書く。書けない概念は粒度が粗すぎるので分ける。
5. 各概念に優先度と抽象度を付ける。
6. 循環があれば解く。循環は、どちらかの定義があいまいなしるし。概念を分けるか、片方を簡単な形で先に出す。

### 2-2. 優先度と抽象度

| 優先度 | 意味                                                        | 扱い                             |
| ------ | ----------------------------------------------------------- | -------------------------------- |
| Must   | ゴールへの道の上にあり、欠けると持ち帰りの1文が成り立たない | 必ず1つの説明として出す          |
| Should | 理解を深めるが、なくても持ち帰りの1文は成り立つ             | 時間があれば出す。なければ補足へ |
| Could  | 関連する知識・発展                                          | 付録か質疑のため                 |

- **格上げ**：Must の前提にある Should・Could は Must にする（前提が欠けると前方参照になるため）。
- **抽象度**：具体（個別の事例・データ・操作・現象。例「売上の記録が重複して入る」）か、抽象（一般化した概念・原則・方針。例「冪等性」）。3章の並べ方と、5章の ADEPT の対象に使う。

### 2-3. 書き方（knowledge-map.md）

`decks/<deck-id>/knowledge-map.md` に表で書く。図（Mermaid など）は使わない（CLAUDE.md 原則3。表なら差分が読める）。見本は `examples/sample-deck/knowledge-map.md`。

```markdown
---
deck_id: 2026-10-17-report-automation
goal: K-007 # 持ち帰りの1文に当たる概念の ID
---

| ID    | 概念             | 1文の定義                            | 前提  | 優先度 | 抽象度 |
| ----- | ---------------- | ------------------------------------ | ----- | ------ | ------ |
| K-001 | 作成時間の現状   | 6部門の作成に月40時間かかっている    | -     | Must   | 具体   |
| K-002 | 時間がかかる理由 | 入力の形が違い、集計を手で直している | K-001 | Must   | 具体   |
```

- 前提は ID を「、」で区切る。なければ「-」。層は書かない（スクリプトが出す）。
- `node .claude/skills/slide-outline/scripts/check-knowledge.mjs decks/<deck-id>` で確かめる。
  - エラー：表の書式、ID の重複、表にない前提、定義がない、優先度・抽象度の値、循環、格上げ漏れ、goal がない・Must でない、「たたき台がある」「相談して決めたい」なのに知識マップがない。
  - 注意：goal につながらない Must（Should にするか、前提の関係を足す）。
- 知識マップは承認の対象ではない。構成を見せるとき（`SKILL.md` 手順 8）に一緒に見せる。

## 3. 説明の順序（2 構成）

### 3-1. 層（基礎から応用へ）

1. Must の概念だけを取り出す。
2. Must の前提がない概念を層0、層0だけを前提にする概念を層1…とする。
3. 層の小さい順に説明する（ボトムアップ）。

`check-knowledge.mjs` が層を出す。

### 3-2. 同じ層の中の並べ方

層の順だけでは並びが1つに決まらない。次の順で決める。

| 順  | 基準                                     | 決めるもの | 理由                                                                                            |
| --- | ---------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| 1   | 次の層でより多くの概念の前提になるもの   | スクリプト | 早く出すほど、あとの説明が楽になる（推測）                                                      |
| 2   | ストーリーの上で、直前の問いに答えるもの | AI と人    | 問いの連鎖を切らない（4章）（推測）                                                             |
| 3   | 具体 → 抽象                              | スクリプト | 具体から始め、はっきりと段階を踏んで抽象へ移す方法（Concreteness fading）が研究で勧められている |

- スクリプトは基準1・3で並べた候補を出す。基準2で入れ替えるかは、構成を作るときに AI が決め、人に見せる。
- 基準3は決まりではなく既定の並べ方。ずっと具体のまま教えたほうが同じか良かった研究もある。聞き手の前提知識が十分なら、抽象から入ってもよい。
- 具体から抽象に移るときは、具体のどの要素が抽象のどこに当たるかをはっきり書く（Concreteness fading の要件）。

### 3-3. 並びを outline.md に移す

- 層の順を、章とスライドの並びの土台にする。1つの概念を1枚とは限らない（1枚に2つ、2枚に1つもある）。
- 層の順と違う並びにしたスライドは、見せるときに理由を書く（`SKILL.md` 手順 8）。冒頭で答えを予告する（4章の SCQA）のは、順序の違反ではない。

### 3-4. 前方参照をしない

決まり：スライド i のタイトル・本文・図・話す内容で使う概念は、すべて前提知識（brief.md）か、スライド 1〜i−1 で説明したものにする。スライド i で初めて出す概念は、そのスライドの中で説明してから使う。

| よい                                                     | よくない                                             |
| -------------------------------------------------------- | ---------------------------------------------------- |
| 前提知識（1章）に書いた概念                              | あとのスライドで説明する言葉を、そのまま使う         |
| 冒頭の予告（目次、SCQA の答え）で、名前だけ出すこと（※） | 「詳しくはあとで」と言いながら、その概念を根拠に使う |
| 説明した概念の言い換え                                   | 図の凡例・注釈に、説明していない言葉を入れる         |
| 聞き手の日常の知識による類推・例                         | 類推・例の中に、説明していない専門用語を入れる       |

※ 予告は例外。あとで説明する言葉は名前を見せるだけにし、根拠には使わない。主な概念の名前と特徴を先に知っていると理解しやすい（Mayer の Pre-training 原則）とも合う。

検査：`outline.md` の各スライドに `new`（初めて説明する概念）と `uses`（使う概念）を知識マップの ID で書く。`check-outline.mjs` が、知識マップがあるときに次を確かめる。

```
各スライド i について：uses(i) ⊆ new(1) ∪ … ∪ new(i−1) ∪ new(i)
（前提知識は知識マップに書かないので、uses にも書かない）
```

- エラー：前方参照、知識マップにない ID、どのスライドでも `new` にならない Must。
- 注意：同じ概念を2回 `new` にした。
- 予告で名前だけ出す概念は `uses` に書かない。根拠に使うなら、そのスライドより前で説明する。

## 4. ストーリー（2 構成）

ストーリーがある状態を、次の4つで決める。

|     | 要件                   | 確かめ方                                                                                                              |
| --- | ---------------------- | --------------------------------------------------------------------------------------------------------------------- |
| S1  | 冒頭で問いが立っている | 最初の2〜3枚で SCQA（状況・問題・問い・答えの予告）を示している（人）                                                 |
| S2  | 問いの連鎖             | 各スライドが直前に生まれた問いに答え、次の問いを生む。`question` の書き漏れは注意（機械）。問いが自然につながるかは人 |
| S3  | 見出しだけで話が通る   | タイトルを順に読むと、1本の文章として意味が通る（人。`story.mjs` の一覧で見る）                                       |
| S4  | 回収                   | 最後に、冒頭の問いにはっきり答えている（持ち帰りの1文に戻る）（人）                                                   |

### 4-1. 冒頭：SCQA

| 要素                 | 中身                       | 例（見本のデッキ）                                   |
| -------------------- | -------------------------- | ---------------------------------------------------- |
| Situation（状況）    | 聞き手が同意できる今の状態 | 各部門の表を本部が手で貼り合わせている               |
| Complication（問題） | 今の状態を崩す変化・課題   | 月40時間かかり、誤りに気づくのが配布のあと           |
| Question（問い）     | 聞き手の頭に浮かぶ問い     | どうすれば作成の手間を減らせるか                     |
| Answer（答えの予告） | 持ち帰りの1文              | 入力をそろえて集計を自動にし、来年度に全部門へ広げる |

解説型でも、SCQA で答えを予告してから、本文は基礎から積み上げる（推奨）。ピラミッド原則は「結論を先に」、知識マップは「基礎から」を求めてぶつかるため、冒頭で答えを予告し（地図を渡し）、本文で基礎から積み上げて両立させる（この両立のさせ方は独自の整理で、推測を含む）。

### 4-2. 本文：問いの連鎖

`outline.md` の各スライドに `question`（このスライドが答える問い）を書く。

- 問いが書けないスライドは、要らないか、順序が誤っている。
- 問いが前のスライドから自然に出ないときは、間に橋渡しのスライドを入れる。
- つなぎの言葉で確かめる：スライドの間を「だから」「では」「しかし」「つまり」のどれかでつなげるか。つながらないところは、話が切れている。

構成を見せるとき（`SKILL.md` 手順 8）に、`node .claude/skills/slide-outline/scripts/story.mjs decks/<deck-id>` の一覧（番号、問い、タイトル、新出、使う）を見せる。話が通るかは人が見る（CLAUDE.md 原則6）。

### 4-3. 説明の順序とストーリーがぶつかったとき

| 状況                                                   | 対処                                                                                   |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| ストーリーでは先に言いたいが、前提をまだ説明していない | 前提を先に説明する（前方参照をしないことを優先する）。橋渡しの問いを入れて流れをつなぐ |
| 基礎が続き、問いが生まれず退屈になる                   | 基礎の章の冒頭に「なぜこれが要るか」の問いを置く（SCQA の問いにつなげる）              |
| 層が深く、枚数が増える                                 | Should の概念を補足へ移す。それでも多ければ、ゴール（1章）を絞る                       |

優先順位：前方参照をしない ＞ 問いの連鎖 ＞ 同じ層の中の並べ方（推測を含む独自の優先付け）。

### 4-4. 提案型のとき：Sparkline

資料の種類が提案型（決めてもらう・動いてもらう）のときは、本文で「今の状態（What is）」と「ありうる姿（What could be）」を交互に見せ、最後に行動の呼びかけ（brief.md の「終わったあとの行動」）で終える。解説型では求めない。

## 5. スライド単位（2 構成）

### 5-1. 1スライド1主張（Assertion-Evidence）

| 要素                | 決まり                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| タイトル（`title`） | 主張を1文で書く（「メダリオン構成」のような名詞だけのタイトルにしない）。例：×「作成時間の内訳」→ ○「作成時間の3割を窓口サービスが占める」 |
| 本文                | タイトルを裏付ける根拠（図・グラフ・表・コード）。箇条書きを並べるだけにしない（`design-reference/principles.md` 5章）                     |
| 主張の数            | 1枚に1つ。2つ以上あれば分ける                                                                                                              |
| 要らないもの        | タイトルの主張を支えないものは削る（Mayer の Coherence 原則）                                                                              |

- 図が本当に要らないスライド（定義を言うだけなど）に、無理に図を入れない。すべての主張に図を求めると、意味のない図が増えるという批判がある。
- 表紙・目次・章の扉・締めと、手順やチェックリストのように見出しが名前で足りる型は、名詞のタイトルでもよい（独自の整理）。
- タイトルが1文の主張かは人が見る（機械では決められない）。

### 5-2. 新しく出す抽象の概念の説明（ADEPT）

知識マップで抽象度が「抽象」で Must の概念を初めて説明するときは、次の順で要素を並べる。1つの要素が1枚とは限らない（1枚で複数の要素を扱ってよい）。

| 順  | 要素                           | 役割                       | 例（データの「層」）                                 |
| --- | ------------------------------ | -------------------------- | ---------------------------------------------------- |
| 1   | A：Analogy（類推）             | 知っているものに結びつける | 浄水場の段階ごとの処理                               |
| 2   | D：Diagram（図）               | 構造を見せる               | 生データ→整えたデータ→集計の流れ図                   |
| 3   | E：Example（例）               | 具体で確かめる             | 売上の記録が層ごとにどう変わるか                     |
| 4   | P：Plain English（平易な定義） | 日常の言葉で言い切る       | 加工の度合いごとに表の置き場を分けること             |
| 5   | T：Technical（技術的な定義）   | 正確な定義に着地する       | 層ごとに変換の責務とスキーマの保証を決めるデータ設計 |

- すべての要素を毎回入れなくてよい。聞き手にとって遠い概念ほど多く入れる。最低限「具体（A・D・E のどれか）1つ以上＋技術的な定義（T）」を入れる（推測を含む独自の最低線）。`outline.md` の `adept` に扱う要素を書き、足りなければ `check-outline.mjs` が注意を出す。
- 類推を使うときは、どこで類推が成り立たなくなるかを一言添える（類推の当てはめすぎを防ぐため。推測）。
- 類推・例の中でも、説明していない専門用語は使わない（前方参照をしない）。
- 3-2 の「具体→抽象」は概念どうしの並べ方、ADEPT は1つの概念の中の説明の並べ方。
- ADEPT は実践者（Kalid Azad）の手法で、実証研究にもとづくものではない。ただ、「具体から抽象へ」の向きは Concreteness fading と合う。

## 6. 確かめ（2 の「見せて、直す」、5 最終確認）

機械で確かめられる項目はスクリプトに入れ、ほかは人の確認表（`design-reference/checklist.md` の「構成」）で見る。AI は人の項目を判定しない（CLAUDE.md 原則6）。

| 項目                                                                        | 確かめ方                                             |
| --------------------------------------------------------------------------- | ---------------------------------------------------- |
| 持ち帰りの1文、前提知識、資料の種類が書かれている                           | 機械（`check-brief.mjs`）                            |
| 前提知識の各項目が、聞き手の過半数に通じる                                  | 機械（割合が5割未満なら注意）＋人（割合の見積もり）  |
| 持ち帰りの1文を30〜45秒で説明できる（エレベーターテスト）                   | 人                                                   |
| 知識マップ：定義・優先度・抽象度がある、循環がない、格上げ漏れがない        | 機械（`check-knowledge.mjs`）                        |
| スライドの並びが知識マップの層の順に従う。違うところに理由がある            | 人（`check-knowledge.mjs` の候補と並べて見る）       |
| 前方参照がない。Must がどれもどこかで説明されている                         | 機械（`check-outline.mjs`）                          |
| 予告で出した言葉を根拠に使っていない                                        | 人                                                   |
| 冒頭の SCQA（S1）、問いの連鎖（S2）、見出しだけで話が通る（S3）、回収（S4） | 問いの書き漏れは機械、ほかは人（`story.mjs` の一覧） |
| タイトルが1文の主張。1枚1主張。主張を支えないものがない                     | 人                                                   |
| 各タイトルに「だから何？」（ゴールへの寄与）を答えられる                    | 人                                                   |
| 新しく出す抽象の Must に、具体と技術的な定義がある                          | 機械（`adept`）                                      |
| 類推に、成り立たなくなる点を添えた                                          | 人                                                   |
